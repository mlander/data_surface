# Two real adopters: pathauto and honeypot settings as resources

The two-adopter gate of the roadmap (confidence in the direction): port
two contrib settings forms we did not write, as resources in sandbox
modules, and record what the pattern could not express or expressed
badly. Ported on `next` (HEAD 6bea3d4) by an agent given the docs and
the forms' source, on 2026-10-19. The sandbox modules are
`ds_adopter_pathauto` (resource `adopter.pathauto.settings`, route
`/admin/config/search/path/surface-settings`) and `ds_adopter_honeypot`
(resource `adopter.honeypot.settings`, route
`/admin/config/content/honeypot/surface-settings`); they are not part
of this repository. Both ports write their own config object with the
original's schema and install values, copied and renamed. The original
modules were installed on the site and were not touched.

Forms chosen:

- **Pathauto 8.x-1.15, `PathautoSettingsForm`:** a punctuation table
  whose rows come from an alterable list, each row's default depending
  on the separator; entity-type checkboxes with per-item disabled state;
  a max-length bound read from a service; safe tokens typed as a comma
  string but stored as a list; an update action as radios.
- **Honeypot 2.2.2, `HoneypotSettingsForm`:** a `#states` dependency; a
  hand-written `validateForm()` with three rules on one field; required
  numbers; a config key the form never shows (`unprotected_forms`); one
  checkbox per form the site has.
- Metatag 2.2.0 was read and set aside: no validation, no `#states`, no
  AJAX.

## What could not be expressed

1. **Per-option state in a list (checked and disabled).** A key can be
   locked whole; a list item cannot. The fixed types are left out of the
   options and named in the description, and "a type with patterns stays
   enabled" is a list constraint added by a runtime refiner. Neither is
   stated in the schema. Gap in the pattern.
2. **Checkboxes and radios.** No stock widget draws either. Radios came
   back through a cosmetic `#type` swap, because they post the same
   scalar. Checkboxes cannot: they post a different shape, and extraction
   belongs to the widget. Gap in the pattern. The cosmetic seam's docs do
   not say that the posted shape must stay the same.
3. **A list of free strings on a Form API form.** No stock widget draws
   one (the build throws); React has `ListField`. The port wrote a
   widget. Gap in the pattern, deferred under "Input shapes".
4. **A default from a sibling key.** The punctuation rows sit behind the
   wall in a child, and their keys are derived, so no refiner can name
   them. The logic moved into storage `load()`. The contract's `default`
   is right only for separator `-`, and only until the first save. Gap,
   small in practice.
5. **Several Regex rules on one key.** Core keeps one constraint per
   name. `Sequentially` validates everywhere, but the emitter states no
   pattern for it, only `checkedOnServer`. Gap: the emitter could state
   composites as `allOf` or `anyOf`.
6. **Descriptions that depend on installed modules** (the help link, the
   Redirect sentence) went to the cosmetic layer, so the tool and the
   contract do not carry them. Deliberate exclusion.
7. **An alter hook that adds entries to a map the owner stores.** Alters
   mount only under `third_party_settings.<module>`. The hook is kept by
   running it inside the deriver. Gap in the pattern.
8. **Presentation** (size, suffix, grouping fieldset, h5 headings, a
   collapsed details) lives in the cosmetic layer. Deliberate exclusion,
   and the seam held.

## What was expressed badly

- **Site-derived keys need a deriver.** The pathauto deriver plus its
  service is 107 code lines, against the original's loop of about 20.
- **"Optional" grows an empty choice.** Optional selects offer "- None -"
  and allow null; the original offers no empty choice. Making them
  required would force a tool caller to send all 33 punctuation rows.
- **Required keys must be resent on every tool call**, even on an edit
  ("values.expire: This property is required.").
- **`#states` became an AJAX rebuild.** With JavaScript off, a declared
  `doesNotApply()` keeps the stored ticks where the original form would
  have saved the untick.
- **Core's maxlength message wins** on the separator.
- **Markup leaks into the machine documents.** Escaped placeholders
  appear in labels ("Double quotation marks (&quot;)"), and raw
  `<br /><strong>` in honeypot's descriptions, in the tool listing, both
  schemas and React.
- **Two engine bugs.** `addConstraint('X')` with no options warned from
  the tool bridge on every derivation (fixed on `next` as c5d0f54). The
  "Depends on" text added to a tool description escapes the description
  ("you&#039;d").

## What was expressed better

- **One set of rules at every door.** Honeypot's `validateForm()` checks
  used to run only in the form. Now the form, the tool, the React
  endpoints and dry runs all refuse with the same sentences.
- **The `#states` rule is a contract.** It is stated in the full schema
  as an if/then, the tool description says "Depends on
  protect_all_forms.", a call that sends forms while protect-all is on is
  refused by name, and React narrows it locally.
- **Silent filtering became a refusal.** "'node' is not an entity type
  Pathauto can enable or disable."
- **safe_tokens is a real list**, and React draws it as add and remove
  rows.
- **Bounds and labeled choices are stated in the schema.**
- **Storage did the right thing unasked.** `unprotected_forms` survives
  every save; stale form ids are dropped on save and kept while the forms
  list does not apply.
- **For free:** a read tool, dry runs, both schemas, a React form, and
  one permission enforced at the route, the form, the tool and the API.

## Verification

The form renders and saves for both (read back with `drush config:get`;
pathauto's safe tokens typed as `alias, url,  path ,` were stored as
`[alias, url, path]`; refusals on the form wrote nothing). AJAX:
unticking protect-all brings the forms fieldset back with its headings.
`tool:run` dry runs refuse and accept as expected, including each
element name rule on its own; real runs wrote values that `config:get`
reads back. The read tool returns the stored values, including the
separator-derived start when punctuation is unstored. Both schema routes
answer 200 for both resources. Both React pages render, honeypot drops
the forms fieldset locally, and the validate and submit endpoints refuse
with the same messages. Not exercised: the help link branch (Help is not
installed) and the "stays enabled" rule (no toggleable type has
patterns).

## Conclusion

**Earned their place:** resource, operation and `ConfigObjectStorage`;
LabeledChoice in its canonical integer spelling, Range and Length; the
declared `doesNotApply()` rule, which is the `#states` port in one line;
a runtime refiner; a constraint with its options resolver, and a custom
widget; derived structures attached by id; the cosmetic layer.

**Never needed:** identity and known keys, shapes, mixins, ports, slots,
collections, alters, access classes, child operations, outputs, secrets,
examples, settings layouts, panels. Both forms needed derivation;
neither used any of the composition features.

**The three gaps a contrib author hits first:**

1. **Keys that come from the site.** They need a deriver; per-option
   state has no spelling, and a hook that adds entries has no alter
   equivalent.
2. **The widget set.** No checkboxes, no radios, no list of free strings,
   and an empty option on every optional select.
3. **More than one rule per key, each with its own message.**
   `Sequentially` drops out of the schema, and core's maxlength message
   overrides the rule's own.
