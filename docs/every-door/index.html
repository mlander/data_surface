Data Surface

One resource, every door

This is a drawing of the examples that ship in the data_surface_examples module, not a live copy of them. Layers draws examples 3 and 4, with the fees of example 10 for access. Most other views, the contract and the doors draw example 3, the settings for one event registration (a venue, a room, a capacity, a ticket and a contact), and example 4, Compliance, a second module that adds a license and stewards. Rules as data draws examples 4 and 7, Reuse examples 4 and 8, Site keys example 9, and Access and Operations example 10.

Layered, then sealed

The owner declares the keys and the rules between them. Other modules contribute under names of their own: they add keys at their own mount, and their rules may narrow the owner's keys but never widen them.

Rules and refiners settle what applies to these values: ahead of time where the answer depends only on the values, per request where it depends on the site. Access locks keys or leaves them out for the account. The build seals the result.

Every door reads that one sealed surface and nothing else, so they agree, and one module changes all of them without touching any. That is the alter contract. Compliance's alterInputs(), from data_surface_examples_compliance, reaches every door this way:

Declare the inputs once

      
A resource says what it takes: its keys, their types and their limits. It says nothing about forms, routes or tools.

      
Everything that needs those values reads the same contract. A form, a React page and an agent accept and refuse exactly the same things.

      
Turn the model, pick a layer above, or change a value below and watch it reach every door.

      
Drawn from example 3: RegistrationStep3Resource.php. Explained in Your first resource.

    


    

      
Today: written twice, and they never meet

      
A form array describes the inputs with their callbacks, its validation and its submit handler. A tool plugin lists the same inputs again, with its own constraints and its own save.

      
Each is real work, and neither reads the other. Another module alters the form. The tool never hears about it, so a call with 150 is saved although the form would refuse it. To close the gap the module has to write its rule a second time.

      
A headless admin has nothing to draw from. The form's rules are PHP callbacks, and the tool's inputs carry no dependencies between keys.

      

      
Change the license below. Only the form's doors light up.

The resource

      
One class declares the inputs and the operations that read and write them. Each key is an ordinary typed data definition with ordinary constraints.

      
Its storage, underneath, loads the current values and commits the new ones, so the resource never knows where they are kept.

      

      
Drawn from example 3: RegistrationStep3Resource.php, RegistrationStep3Storage.php. Explained in Declaring a resource.

    


    

      
Structures

      
A resource can attach a structure at one of its keys. The child keeps its own keys, refinement and validation, and the parent cannot reach into it. That is what makes Contact reusable anywhere.

      
Variants are the structures a key can hold when another key's value chooses between them. Pricing decides whether the ticket is the free ticket or the paid ticket.

      

      
Drawn from example 3: FreeTicketStructure.php, PaidTicketStructure.php, ContactStructure.php. Explained in Children.

    


    

      
Refinement

      
Some keys are only fully known once another value is. A refiner is a method that names the key it narrows. Its parameters are the keys it watches, so the signature is the dependency.

      
A refiner may only tighten what was declared. Room narrows to the venue's rooms, and capacity stops at the room's seats.

      

      
Drawn from examples 2 and 3: RegistrationStep3Resource.php, Venues.php. Explained in Refining.

    


    

      
Others get a say

      
Another module can add keys to a resource it does not own, stored under its own name. It can tighten the owner's keys and say where its fieldset is drawn.

      
Here Compliance attaches its own structure, a license and stewards, and wires the structure's capacity to the owner's. Without a license it holds capacity at 100. The owner's class is not touched.

      

      
Drawn from example 4: RegistrationComplianceAlter.php, ComplianceStructure.php, License.php. Explained in Alters.

    


    

      
Declare the rule

      
A rule whose condition and effect a schema can state is declared as data beside the keys. Compliance holds the capacity at 100 with narrow('capacity')->when(Condition::absent('license'))->constrain('Range', ['max' => 100]). The room's ceiling stays a coded refiner, capacityOfRoom(), which the emitter runs once per room to list its answers.

      
A rule is not run: the full schema writes it as an if / then and lists it under x-surface.rules, so the capacity is stated exactly. The stewards watch the capacity, a number no list covers, so they stay refine: a client asks again with its values.

      
A key can also not apply. While the bulletin goes out monthly, its send day is not on the form or in the documents, and storage keeps the stored day.

      

      
Drawn from examples 4 and 7: RegistrationComplianceAlter.php, BulletinResource.php. Explained in Declaring a rule.

    


    

      
Reuse: one definition, two sites

      
A structure names no key of the resource that holds it. What it needs from there it reads through a port, and each container wires the port to a key of its own. Example 8's person reads listed: the press page wires it to public, the information desk to in_program. Compliance reads capacity the same way.

      
Each document writes the person once, as event.person under $defs, with its port. Each site says which key the port reads, x-surface.reads, and states the email rule on its own allOf.

      
A mixin is merged flat: the review's two keys are the press page's own, stored beside public and refused as reviewed_by. A shape is one named value: the phone is event.phone, used by the person and by the desk, and the license is event.license.

      

      
Drawn from examples 4 and 8: PersonStructure.php, PressResource.php, InfoDeskResource.php, ReviewStructure.php, PhoneNumber.php, ComplianceStructure.php. Explained in Ports.

    


    

      
Keys from the site

      
Example 9 has one checkbox and one set of limits per ticket type the site sells. The class cannot list the types. The site's configuration does, and a provider, TicketTypes, reads it at every build.

      
The provider declares what it read, the configuration's cache tag, so the form, both documents and the tool listing are cached by that tag. Add a VIP type to the configuration and reload: its checkbox, its limits and its row in the tool listing appear, with no cache rebuild.

      
The speaker type is locked in the configuration. It is drawn fixed and is readOnly in both documents. A value a tool sends for it is not taken, and the answer says so in a note.

      

      
Drawn from example 9: TicketSalesResource.php, TicketLimitStructure.php, TicketTypes.php. Explained in Keys that come from the site.

    


    

      
Who may change what

      
The fees of example 10 name an access class. The kind of its answer is read from the answer's cacheability, never declared: an answer that varies by user.permissions alone is static, and one that reads a stored value is runtime.

      
A static answer is stated ahead, for the account that asks. Without "set event fees", the fees are locked: readOnly in the full schema and in the tool listing. With the workflow module on, an account without "see event fees" gets no fees at all.

      
For any other account the stored program decides: once it is published, the fees are fixed. The full schema marks them access: "live", and the schema for these answers, the form and the pipeline settle it per request.

      

      
Drawn from example 10: FeesStructure.php, FeesAccess.php, FeesWorkflowAlter.php. Explained in Static and runtime access.

    


    

      
What an operation says about itself

      
#[Operation] says whether a call creates, changes nothing or may destroy, and whether repeating it changes anything more. Both documents state these facts at the top, under x-surface.operation. Example 10's check declares readOnly: TRUE, which the documents state as kind: "read".

      
The Tool API gives a read only operation the Read kind and every other operation the Write kind. An MCP client reads its hints from that kind and from the destructive flag. Checking changes nothing, so it has no read tool beside it.

      
The Tool API keeps idempotence on the kind, and no kind that writes is idempotent. Configuring is idempotent in both documents and reaches an MCP client as not idempotent.

      

      
Drawn from example 10: ProgramResource.php. Explained in Operations.

    


    

      
The contract

      
Ask the resource and it answers in JSON Schema, contract 3, as two documents. The schema as it stands is built for the values so far. The full schema reads no value, so it is the same whatever is stored or typed; access in it is the asking account's.

      
Labeled choices are oneOf. A key's variants are an anyOf of their defs, each chosen by a conditional. A declared rule is an if / then listed under x-surface.rules. Where a rule cannot be stated, the key says refine (ask again with values) or live (settled at runtime).

      

      
Drawn from examples 3 and 4: RegistrationStep3Resource.php, RegistrationComplianceAlter.php. Explained in Two documents.
