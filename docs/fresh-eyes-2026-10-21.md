## (b) The three doc changes that would have helped most

1. first-resource.md: give the real order for a new module. The generator refuses a module that is not installed, and installing first leaves no config object, so the steps are: write the classes, install, `config-schema --write`, reinstall (or import the install file). For an owner plus an alter module: install both, write the owner, write the alter's module, reinstall both. Say that the warning printed between those two writes is expected.
2. A short "a settings page with a reused part and an alter" walkthrough, the size of second-resource.md, that strings together Shape, `attach()` with a port, a declared rule on the port, an alter adding a key, and an alter answering access. Each piece is documented well, but they are spread over resources.md (1,900 lines), refinement.md, storage.md and declaring-a-resource.md, and I had to assemble the order myself.
3. Put the regex subset both engines read alike on served-contract.md (or recipes.md) instead of only on decisions.md, and say there how `after:` behaves when the named key sits in an arrangement group. Also settle recipes.md versus storage.md on whether a text area is `text` or `string` in config schema.

## (c) Verdict

For the contract half, yes today: the tool, the read tool and both JSON Schema documents came out right from one class, every wrong call came back with a path, a stable code and a sentence naming what it depends on, and the full schema stated the hourly rule, the port rule and the shape exactly. For the form half, mostly yes: groups, suffixes, placeholder, radios, checkboxes, time inputs, AJAX narrowing and server messages all worked with no form code, but `after:` placement failed on the Form API page while it worked in React, and the install order cost me a reinstall. I would use it for a settings form in a real project now if the project can carry an experimental dependency, because the class is about a third of the code of the hand-written equivalent and the agent-facing contract comes for free; the risk is in the generated-files workflow and the edge cases between doors, not in the core model.

## (e) The tool answers

Every wrong call that reached the tool gave me enough to fix it in one step: the path said which key (down to `amenities.1` and `insurance.policy_number`), the message said what was allowed for the values sent, including the computed deposit maximum ("from 0 to 150 ... This applies when daily_rate is 300") and the container key a port reads ("when daily_rate is 1500"), and my own Regex messages came through unchanged. Two answers were weaker: a refused item in a multi-select says only "not a valid choice" with no list of allowed values, unlike a single choice, and a misspelled key says "Unknown key venue_nmae." with no near match. The two calls the Tool API refused before the tool ran (a non-integer deposit, a string for a number) came back outside the result shape with no code and "should be of the correct primitive type", which does not name the type wanted; the tool README warns about this, but it is the one case where a caller needs a second look. The codes helped: `required`, `does_not_apply`, `no_such_choice`, `not_in_range`, `too_low`, `too_long`, `regex_failed`, `unknown_key` and, for the season lock, `locked` at path `""` each tell a caller what kind of fix is needed without parsing the sentence, and `locked` at the empty path makes "nothing you send will work" distinguishable from a bad value.
