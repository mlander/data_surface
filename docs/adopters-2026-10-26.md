# Adopter log: pathauto's settings form, second port, 2026-10-26

On 2026-10-26 I ported `PathautoSettingsForm` from pathauto 1.15 onto
Data Surface, branch `next` at e14f0cd, on the `drupal-8-22` site. The
result is the sandbox module `ds_adopter_pathauto_two`: the resource
`adopter.pathauto_two.settings` at
`/admin/config/search/path/surface-settings-two`, writing its own config
object `ds_adopter_pathauto_two.settings`, whose schema and install file
are pathauto's, copied and renamed. I had not used the module before. I
read the module README, the pages under `docs/` and the submodule
READMEs, and the pathauto form with its schema and install file. I did
not read the tests, the earlier ports, the review, fresh-eyes or adopter
logs, `CLAUDE.md` or `ROADMAP.md`. Each time I opened Data Surface source
is an entry below.

## What could not be expressed

1. **Entry defaults under a stored map, on the form.** The operation form
   merges declared defaults under stored values one level deep, so an
   entry missing from a stored map is drawn empty and saved as `null`.
   [Maps](semantics.md#maps) promises the opposite. I made the storage's
   `load()` answer each map whole, asking each provider for its entries
   and filling the unstored ones with the entry's default. That is nine
   lines and a class resolver in a storage that should only name its
   object.
2. **A key asked one way and stored another, on a config object.** There
   is no layout seam on `ConfigObjectStorage` and no documented way to
   tell the schema check that a key is translated. I overrode `load()`,
   `prepare()` and `widerThanSchema()`. The schema generator does not
   know about the translation either: `drush data_surface:config-schema
   --module=ds_adopter_pathauto_two` would write `enabled_entity_types`
   as a sequence of booleans, so the drift check fails for good on this
   module.
3. **A comma list widget.** No stock widget; I wrote one (33 lines). The
   served contract states `x-surface.widget: "list"`, not my widget, so
   React draws rows and only the Drupal form shows the text area. The
   tool and HTTP take and answer a JSON list, which is better than
   pathauto's string.
4. **Pathauto's submit filter.** "Never store a type whose path field
   another module provides" is a rule of storage, not of the contract.
   It lives in `prepare()`, so a caller sends `node: true`, is told it is
   locked, and nothing in either schema says the value will not be
   stored.
5. **Markup in a label.** Pathauto titles each punctuation select
   `Name (<code>char</code>)`. A label is in both schemas and the tool
   listing, so I wrote `Name (char)` as plain text.

## What was expressed badly

1. **Two nested "Punctuation" details.** The map draws its own open
   `details`, and the collapsed group I asked for wraps it, so the page
   shows "Punctuation" inside "Punctuation". There is no way to collapse
   the map's own element.
2. **"- None -" on every choice.** Pathauto's schema is not fully
   validatable, so every key may hold nothing: the update action gains a
   "- None -" radio, each punctuation select a "- None -" option, and the
   tool accepts `null` for each. Correct by the documented rule, and
   wider than pathauto's form.
3. **Locked entries in the listings.** `drush tool:info` leaves the
   Locked column blank for the locked entity types (the catalog and the
   full schema mark them), and the schema's def for those entries states
   no default.
4. **Punctuation is deferred.** Thirty-three characters pass
   `site_list_limit` (20), so the tool listing and the full schema state
   the map open and list the ids; an agent fetches the schema per entry.
   Documented and reasonable, but an agent reads less than a person sees.
5. **Descriptions with links.** The help and redirect links are read from
   the module list inside `defineInputs()`, with no cache dependency
   declared, since I could not tell which tag the docs want for "a module
   is installed". The schema strips the links to text, which is right.

## Verdict

**The contract half: yes.** One class says what pathauto's form says,
and the tool, HTTP, the schema and the form refuse the same values in
the same words, by path. Locked entries, keys from the site with their
cache tags, labeled integer choices and a dry run all came from stock
pieces, and the docs led me to each. That is worth adopting on a real
project for any settings object an agent or a deploy script also
writes. **The form half: not yet, for a form like this one.** The
generated form lost every unstored entry's default until I patched my
storage, nested two details where I asked for one, and offered "- None
-" on every choice. A form with a map of keys from the site needs the
form builder's merge fixed first. A plain settings page, as in First
resource, I would generate today.

The three doc changes that would have helped most:

1. **A recipe for a key asked one way and stored another on a config
   object**: override `load()` and `prepare()`, and tell the schema
   check with `configSchemaPaths()` or `widerThanSchema()`, with the
   generator's behavior for such a key stated.
2. **The `SiteList::add()` signature on the keys-from-the-site page**,
   with `default:` and `locked:` in one snippet, and a sentence on what a
   stored map missing an entry does on each door.
3. **A sentence on what `defineInputs()` may read**: whether the module
   list and route generation are allowed, and which cache dependency a
   description that depends on an installed module should declare.
