## (b) The three changes to the docs that would have helped most

1. Give every snippet its `use` lines, or a single "imports" table on concepts.md (class -> namespace). The keys-from-the-site provider (KeysFromSiteInterface, KeyedList) appears nowhere with a namespace, in no doc and in no shipped submodule; I found it only by `find src`. The named-shape section also omits the `use` lines for `#[Shape]` and ShapeInterface.
2. Ship one fully validatable config schema on an allowed page, and say what FullyValidatable asks of the author beyond `nullable: true` (every key required unless `requiredKey: false`, a constraint on each leaf, how to check it). storage.md points at the opening-hours fixture, which a reader outside the repo's tests cannot be expected to open.
3. In recipes.md's "applies only when ... and is then required", add the list case: for a list, required is satisfied by `[]`, so "at least one when weekly" is a `Count` min 1 (or a declared `constrain('Count')` rule), and say next to `->require()` that a key left out keeps what is stored, so a rule requiring it only refuses a key sent empty or one with nothing stored.

## (c) Verdict

For the contract half, yes, today: one class per thing gave me a form, a tool, two JSON Schemas and a React page that agree with each other, every rule I declared came back stated in the full schema and refused at every door in its own words, and keys that follow the site with a locked one took twenty lines. For the form half, mostly yes for an admin settings page: every element I asked for was stock and correct with no form code, but the form's required message is core's rather than the rule's, and anything beyond what the stock widgets draw means learning the widget plugin and cosmetic layer, which I did not need here. The reason I would still hesitate on a real project is that every submodule is `lifecycle: experimental` and the API surface (alters, mounts, ports, slots) is large, so I would adopt it for settings pages first and keep an eye on the decisions page before going further.

## (e) The refusals

Yes, every wrong call told me enough to fix it in one step: each refusal names the key by its full path (`sender.name`, `third_party_settings.ds_fresh_eyes_three_extras.footer`), says the rule in the words I or the constraint gave it, and, for a conditional rule, names the condition that made it apply ("when Digest frequency is Daily", "does not apply when Digest frequency is Monthly"), so I knew whether to change the value or the key it depends on. The two weaker answers are the structure rule's "Name is required when Email is digest@example.com", which names the email's value where the condition is any email, and the locked content type, where a value sent for it is accepted and silently dropped with no word in the answer, so a caller does not learn its change was not taken. The Tool API's own refusal for a missing required key ("values.reply_to: This property is required.") and the access refusal (which even says to pass --uid) were the clearest of all.
