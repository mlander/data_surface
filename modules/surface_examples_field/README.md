# Surface API examples - Field settings

Core's field instance and field storage settings as resources:
`field.instance`, a field on a bundle, and `field.storage`, the storage
it attaches. Each field type's settings are a variant of the field's
`settings` key: the settings class a field type's module marks with
`#[Variant]`, or one read from the field type's config schema. With the
Tool API door open (the [Tool](https://www.drupal.org/project/tool)
module installed), the field is `surface:field.instance:create`,
`:reuse` and `:update` and `surface:field.storage:update`, whose
`settings` are the field type's own settings variant where it has one,
so the A/B against the free-form Tool Belt tools is a fair one: the same
question, "what may the settings be?", answered from a contract instead
of a config schema.

This module applies the pattern to a thing core already has, to test it
across scenarios. It is not part of the project and will not ship in
this form. The Tool API door itself is the base module's
([The Tool API door](../../docs/tools.md)).

## The rename

The hand-written `surface:field_add` and `surface:field_update`
are gone, replaced by the tools derived from the field instance
resource's operations. Nothing about the settings changed: the same
variant sits at the same key, and the comparison below is the same
document. What a caller sends moved:

| Was | Is | Inputs |
| --- | --- | --- |
| `surface:field_add` (an existing storage) | `surface:field.instance:reuse` | `entity_type`, `bundle`, `field_name`, `values` |
| none (a new storage) | `surface:field.instance:create` | `entity_type`, `bundle`, `values` (with `field_type`, `field_name`, `storage`) |
| `surface:field_update` | `surface:field.instance:update` | `entity_type`, `bundle`, `field_name`, `values` |

Each tool takes the field by its parts, the names core's field config
stores them under: create the bundle it adds to, reuse and update the
whole field, `surface:field.storage:update` the entity type and the
field name. A parameter is identity the caller knows, so no tool asks
for a composite id such as `node.article.body`, and each part says what
it is, as the key of the same name does
([decision](../../docs/decisions.md#a-parameter-is-identity-the-caller-knows)).
A part that names nothing is refused naming it, to an account holding
the field permission for the entity type sent; any other gets the one
fixed refusal.

`values` holds what used to be top-level inputs (`label`,
`description`, `required`, `settings`) beside `storage` (cardinality,
translatability, and the storage settings its field type chooses, such
as a string's `max_length`), and every tool takes `dry_run`, which runs
storage's own checks and writes nothing, and answers the accepted
`values` as the read tool would: what storage would have been handed is
never served, since it holds what the caller may not see
(why: [decision](../../docs/decisions.md#every-door-projects-what-the-read-tool-projects)). The
field type key offers every field type offered in the UI. One whose
module marks a settings class with `#[Variant]` is described
by that class; every other, a plain `string` or `integer` field
among them, is described by its config schema,
`field.field_settings.<field type>`, through `FieldSettingsSchemaVariants`
(below): its keys, their types and labels, and the field type's own
default settings where their type fits, and nothing more. The storage
settings are the same kind of variants on the storage, described by
`field.storage_settings.<field type>` through
`FieldStorageSettingsSchemaVariants`. The tools place a new field on the
bundle's default form and view displays, as the old field add tool did.

## What it shows

Tool Belt's `field_add` refines `settings` from the field type's config
schema once the field type is known, which for the `address` field type
yields three types, a nested `override` key with nothing to put a
property name in, a deprecated `fields` key offered as an ordinary one,
and no vocabulary, labels or defaults anywhere below the top level.

Here the same input is converted from the settings the field type
declares. [`COMPARISON.md`](COMPARISON.md) holds both JSON Schema
documents side by side, `values.settings` of
`surface:field.instance:reuse` and `settings` of
`tool_belt:field_add`, generated by `scripts/generate-comparison.php`;
`FieldToolsComparisonTest` asserts the checked-in file has not drifted
rather than written by hand, and that the derived tools say at least
what the retired ones did.

Three pieces:

- `Resource\FieldInstanceResource`: a field on a bundle, in the new
  spelling, with `create`, `reuse` and `update` operations, a storage class
  and an access class. It attaches `Resource\FieldStorageResource` at
  `storage` (its field type, cardinality, translatability and storage
  settings, with storage of its own, committed before the field), and its
  `settings` are variants chosen by `field_type`: the settings class a
  field type's module marks with `#[Variant]` (the address module's, and
  the test module's gated one), and for every other field type the one
  `FieldSettingsSchemaVariants` derives. `reuse($entity_type, $bundle,
  $field_name)` is a create for the field and an update for its storage;
  the storage's update operation, `update($entity_type, $field_name)`,
  knows the storage's identity, the field type among it, which locks its
  settings to that type's, and refuses
  shrinking its cardinality once the field has data. Adding a field
  leaves the type open on the storage as on the field: a caller setting
  storage settings names it on both, and the storage refuses a type
  other than the field's. A settings change that would alter the
  database columns of a field with data is refused when the storage is
  prepared, where the SQL storage would otherwise throw on save. Executing
  submits the whole field instance resource to its composed storage,
  which prepares every part (the storage, the field, the settings)
  against its config schema, then writes the storage if it moved, the
  field, and, through the settings variant's own storage where it names
  one, its settings.
- `FieldSettingsSchemaVariants`: the provider the field instance
  resource's `attachVariants('settings', by: 'field_type', from: ...)`
  names, a `SiteListInterface` listing one variant per field type offered
  in the UI, labeled with the field type's label, its schema
  `field.field_settings.<field type>` written as JSON Schema
  (`ConfigSchemaDocument`) for the schema reader, with the field type's
  own default settings where their type fits; a `#[Variant]` wins for
  its value. `FieldStorageSettingsSchemaVariants` is the same class
  pointed at the storage resource's `settings`,
  `field.storage_settings.<field type>` and the field type's default
  storage settings. A variant from the site has no storage of its own,
  so the field, or the storage, stores it. It is a list the site
  decides: past `surface.settings:site_list_limit` field types both
  documents state `settings` open and `deferred`, fetched per field type,
  and the tools never spell it out: they state the stored field type's
  settings, once a field is named, and name the fetch and the narrowing
  tool for any other.
- The tools themselves are the base module's Tool API door, derived
  from these resources' operations as from any other's
  ([The Tool API door](../../docs/tools.md)).

### One deliberate difference from the Tool Belt pair

Tool Belt's update tool strips every null from the settings it is given
before merging them over the stored ones, so a setting can be set but
never cleared. Here the pipeline merges the payload over what storage
loads, key by key and at every depth, and a null is a value like any
other. Sending `{"label": "Address", "settings": {"field_overrides":
{"organization": null}}}` to the update tool removes that one override and
leaves the rest alone, which is what a caller correcting one mistake
actually wants to say. A key left out keeps what is stored; a null
clears it (why: [decision](../../docs/decisions.md#absent-keeps-null-clears)).
A secret is the one exception: it is optional, a null or a key left out
keeps the stored secret, and only the clear marker
(`@surface:clear-secret`) empties it. The label could be left out
too: the update tool requires no key, and a required one left out keeps
what is stored, which the pipeline judges
([The Tool API door](../../docs/tools.md#notes-for-the-tool-api)).

## How to try it

```bash
composer require drupal/tool drupal/address
drush pm:install tool surface_examples_field surface_examples_address
drush tool:list
```

`drush tool:info surface:field.instance:reuse` prints the input
definitions. The `values` input's `settings` carry every field type's
settings until the field is known, and refine into the address settings
once `entity_type` and `field_name` name an address storage. Compare
with `drush tool:info tool_belt:field_add` on the same site, or read
[`COMPARISON.md`](COMPARISON.md), which has both. What a tool takes,
answers and lists is the same for every resource:
[The Tool API door](../../docs/tools.md).

## Note for core

`TypedDataManager::getPropertyInstance()` caches item prototypes by root
data type and property path, not by field config object, so asking two
different unsaved `FieldConfig` objects for their first item hands back
two clones of the first one's item, and storage built for the second
writes to the first one's entity. A tool hits this immediately, because
it describes an unsaved field while refining its inputs and creates
another while executing. The field type trait sidesteps it by building
the item straight from `FieldConfigBase::getItemDefinition()`, which a
field config caches on itself and binds to itself.

This note and the [notes for the Tool API](../../docs/tools.md#notes-for-the-tool-api)
are summarized in [`docs/core-gaps.md`](../../docs/core-gaps.md).
