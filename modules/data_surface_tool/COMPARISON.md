# Two settings inputs for one field type

Generated by `scripts/generate-comparison.php`; do not edit by hand.
`FieldToolsComparisonTest` asserts on every run that this file still
matches what that script produces, so an edit here is a test failure
rather than a quiet fork.

Both documents below are the `settings` input of a field add tool, for
the `address` field type on `entity_test`, after the entity type, bundle
and field name are known. Both were produced by the Tool API's own
definition serializer normalizing the tool's inputs to JSON Schema,
which is the document an MCP client or a function calling model is
handed. The tools take the same seven inputs; only where the settings
input comes from differs.

What to look at:

- `field_overrides`. The surface names all twelve address properties
  that may be overridden, each with a label and the three values it
  takes. The config schema says it is an array of objects with one
  `override` key and no way to name the property being overridden, so
  the single thing a caller most wants to say cannot be said.
- `available_countries`. The surface resolves the country list live, so
  the list that validates is the list that is offered. The config schema
  says "array of string".
- `fields`. The config schema offers it as an ordinary key. It is
  deprecated, and it silently overrules `field_overrides` whenever it is
  not empty. The surface does not offer it, and every write through the
  surface stores it empty.
- Labels. Both carry the top level ones, because the config schema
  happens to label its four keys. Nothing below the top level is labeled
  on the config schema side, and nothing anywhere carries a vocabulary.
