# Data Surface - Tool API bridge

Tools generated from resources: one per operation of every resource that
can be asked on its own, `data_surface:<resource>:<operation>`, and a
read tool beside each that changes a thing that exists,
`data_surface:<resource>:<operation>:read`. For a
field that is `data_surface:field.instance:add`, `:reuse` and `:edit`,
whose `settings` are the field type's own settings variant where it has
one, so the A/B against the free-form Tool Belt tools is a fair one: the
same question, "what may the settings be?", answered from a contract
instead of a config schema.

## The rename

The hand-written `data_surface:field_add` and `data_surface:field_update`
are gone, replaced by the tools derived from the field instance
resource's operations. Nothing about the settings changed: the same
variant sits at the same key, and the comparison below is the same
document. What a caller sends moved:

| Was | Is | Inputs |
| --- | --- | --- |
| `data_surface:field_add` (an existing storage) | `data_surface:field.instance:reuse` | `storage` (`<entity type>.<field name>`), `bundle`, `values` |
| — (a new storage) | `data_surface:field.instance:add` | `entity_type_id`, `bundle`, `values` (with `field_type`, `field_name`, `storage`) |
| `data_surface:field_update` | `data_surface:field.instance:edit` | `field` (`<entity type>.<bundle>.<field name>`), `values` |

`values` holds what used to be top-level inputs (`label`,
`description`, `required`, `settings`) beside `storage` (cardinality,
translatability, and the storage settings its field type chooses, such
as a string's `max_length`), and every tool takes `dry_run`, which runs
storage's own checks and writes nothing, and answers the accepted
`values` as the read tool would: what storage would have been handed is
never served, since it holds what the caller may not see
([decision](../../docs/decisions.md#every-door-projects-what-the-read-tool-projects)). The
field type key offers every field type offered in the UI. One whose
module marks a settings class with `#[Variant]` is described
by that class; every other, a plain `string` or `integer` field
among them, is described by its config schema,
`field.field_settings.<field type>`, through `FieldSettingsSchemaVariants`
(below): its keys, their types and labels, and the field type's own
default settings where their type fits, and nothing more. The storage
settings are the same kind of variants on the storage, described by
`field.storage_settings.<field type>` through
`FieldStorageSettingsSchemaVariants`. The tools place a new field on the
bundle's default form and view displays, as the old add tool did.

## What it shows

Tool Belt's `field_add` refines `settings` from the field type's config
schema once the field type is known, which for the `address` field type
yields three types, a nested `override` key with nothing to put a
property name in, a deprecated `fields` key offered as an ordinary one,
and no vocabulary, labels or defaults anywhere below the top level.

Here the same input is converted from the settings the field type
declares. [`COMPARISON.md`](COMPARISON.md) holds both JSON Schema
documents side by side, `values.settings` of
`data_surface:field.instance:reuse` and `settings` of
`tool_belt:field_add`, generated by `scripts/generate-comparison.php`;
`FieldToolsComparisonTest` asserts the checked-in file has not drifted
rather than written by hand, and that the derived tools say at least
what the retired ones did.

Five pieces:

- `Resource\FieldInstanceResource`: a field on a bundle, in the new
  spelling, with `add`, `reuse` and `edit` operations, a storage class
  and an access class. It attaches `Resource\FieldStorageResource` at
  `storage` (its field type, cardinality, translatability and storage
  settings, with storage of its own, committed before the field), and its
  `settings` are variants chosen by `field_type`: the settings class a
  field type's module marks with `#[Variant]` (the address module's, and
  the test module's gated one), and for every other field type the one
  `FieldSettingsSchemaVariants` derives. `reuse($storage, $bundle)` is an add for the
  field and an edit for its storage; the storage's edit operation knows
  the field type, which locks its settings to that type's, and refuses
  shrinking its cardinality once the field has data. Adding a field
  leaves the type open on the storage as on the field: a caller setting
  storage settings names it on both, and the storage refuses a type
  other than the field's. A settings change that would alter the
  database columns of a field with data is refused when the storage is
  prepared, where the SQL storage would otherwise throw on save. Executing
  submits the whole field instance resource to its composed storage,
  which prepares every part (the storage, the field, the settings)
  against its config schema, then writes the storage if it moved, the
  field, and, through the settings variant's own storage where it names
  one, its settings.
- The generated tools: `Plugin\Derivative\ResourceOperationToolDeriver`
  and `Plugin\tool\Tool\ResourceOperationTool`, with `OperationInputs`
  describing them. Here that is `data_surface:field.instance:add`,
  `:reuse` and `:edit` and `data_surface:field.storage:edit`; the node
  type demo adds `data_surface:node.type:add` and `:edit`, and
  `data_surface_entity` one `add` and one `edit` per content entity
  bundle with a form display, `data_surface:entity.content:node.page:add`. The inputs
  are the operation's parameters (an entity parameter as its id; a
  scalar one named for a resource key described as that key), the
  resource's keys the operation does not know as `values`, and
  `dry_run`; see `docs/resources.md`, Tools. Two rules leave an operation
  out: `field.storage`'s `add` asks `administer %entity_type_id fields`
  and no parameter supplies the entity type, so it could never be
  allowed and is only ever a field's; and a structure a plugin names
  with `#[UsesStructure]` is configured through the plugin's host. Only
  a resource that names its storage is a tool. Beside the
  edit tools is a read tool, `Plugin\tool\Tool\ResourceOperationReadTool`
  (below).
- `FieldSettingsSchemaVariants`: a service tagged
  `data_surface.derived_variants` that adds the field instance
  resource's `settings` variants for every field type offered in the UI
  that no `#[Variant]` declares, reading `field.field_settings.<field
  type>` through typed config: a mapping becomes a map, a sequence a
  list, a primitive its typed data type, and what the schema cannot
  resolve without a value `any`. `FieldStorageSettingsSchemaVariants`
  is the same class pointed at the storage resource's `settings`,
  `field.storage_settings.<field type>` and the field type's default
  storage settings. A derived variant has no storage of its own, so the
  field, or the storage, stores it. The catalog says, per key with
  variants, where derived variants come from.
- `InputDefinitions`: converts core data definitions into the
  Tool API's input definitions: type, label, description, required,
  default value and constraints, with maps and lists becoming the Tool
  API's own map and list input definitions.
- The tool contains no settings logic: refining is a build plus a
  conversion, and executing is one call to
  `DataSurfacePipeline::submit()`, which accepts, validates, prepares and
  commits.
- What a write tool takes and answers: [below](#what-a-tool-answers).

### One deliberate difference from the Tool Belt pair

Tool Belt's update tool strips every null from the settings it is given
before merging them over the stored ones, so a setting can be set but
never cleared. Here the pipeline merges the payload over what storage
loads, key by key and at every depth, and a null is a value like any
other. Sending `{"label": "Address", "settings": {"field_overrides":
{"organization": null}}}` to the edit tool removes that one override and
leaves the rest alone, which is what a caller correcting one mistake
actually wants to say. A key left out keeps what is stored; a null
clears it ([decision](../../docs/decisions.md#absent-keeps-null-clears)).
A secret is the one exception: it is optional, a null or a key left out
keeps the stored secret, and only the clear marker
(`@data_surface:clear-secret`) empties it. The label could be left out
too: the edit tool requires no key, and a required one left out keeps
what is stored, which the pipeline judges (below).

## What a tool answers

A write tool answers a run in the one result shape every door answers
([decision](../../docs/decisions.md#one-result-at-every-door)), on a
refusal as on a success, as its result's context, which `drush tool:run
--json` prints as `outputs`. Every key is declared as an output, with a
description, and always present:

| Key | Holds |
| --- | --- |
| `ok` | Whether nothing was refused. |
| `committed` | Whether the values were written; false for a dry run, a refusal and a read only operation. |
| `changed` | Whether the write moved a stored value; false when the values were what is stored, and then nothing was saved. |
| `changes` | The JSON Pointer of each stored value the write changed, or a dry run would, so writing back what the read tool returned changes nothing ([decision](../../docs/decisions.md#absent-keeps-null-clears)). |
| `values` | The accepted values, as the read tool would answer them after the write: no secret, no key this account may not see, and no key never stored that the write left at its default (a mounted key not sent). |
| `violations` | Each refusal, `{path, code, message}`; a refusal of the whole call has an empty path. |
| `notes` | Each value sent for a locked key and not taken, `{path, code, message}`, code `locked`. |
| `stale` | Each stored value kept that may no longer be chosen, `{path, code, message, stored}`, code `stale`. |

The codes are a table in [Value semantics](../../docs/semantics.md#codes):
a constraint's (`not_in_range`, `no_such_choice`, `too_long`), or the
module's own (`required`, `does_not_apply`, `unknown_key`,
`type_mismatch`, `locked`, `access`, `permission`, `not_found`). A
message names a key it depends on by its path and a value by what is
sent with its label beside it, the vocabulary of the listing. The
resource's own outputs, from `defineOutputs()`, follow the shape, and
never take one of its keys.

The result's text says the same for a reader: one line per violation,
"path: message", after "The values were refused:", a refusal of the
whole call its message alone on its line, and a line per note after.
Example 3, a room of another venue and a capacity too large, as a dry
run:

```
drush tool:run data_surface:registration.step3:configure --uid=1 --json \
  --input='{"values":{"room":"harbour_deck","capacity":500},"dry_run":true}'
```

```json
{"success": false,
 "message": "The values were refused:\nroom: The value you selected is not a valid choice. This applies when venue is riverside (Riverside Hall). Choose riverside_main (Main hall) or riverside_east (East room).\ncapacity: This value should be between 1 and 100. This applies when room is empty (harbour_deck was refused) and third_party_settings.data_surface_examples_compliance.license is empty.",
 "outputs": {
   "ok": false, "committed": false, "changed": false, "changes": [],
   "values": {"title": "Spring meetup", "open": true, "venue": "riverside", "room": "harbour_deck", "capacity": 500, ...},
   "violations": [
     {"path": "/room", "code": "no_such_choice", "message": "The value you selected is not a valid choice. This applies when venue is riverside (Riverside Hall). Choose riverside_main (Main hall) or riverside_east (East room)."},
     {"path": "/capacity", "code": "not_in_range", "message": "This value should be between 1 and 100. This applies when room is empty (harbour_deck was refused) and third_party_settings.data_surface_examples_compliance.license is empty."}],
   "notes": [], "stale": []}}
```

A refused value is in the Tool API's `Input` category; a permission
refusal, an access refusal and a resource locked whole are in the
`Access` category, which no client treats as correctable, so none is
handed the input schema to retry with
([decision](../../docs/decisions.md#every-door-projects-what-the-read-tool-projects)).
A read only operation's tool takes no `dry_run` and answers the same
keys, `committed` and `changed` false and `changes` empty: it writes
nothing. The read tool answers a read, `values` alone, and its
refusals in the shape.

`values` is always sent, an object and never null: `{}` on an update
changes nothing. The Tool API refuses a call that leaves it out or
sends `null` before the tool runs
([decision](../../docs/decisions.md#required-is-the-resources-and-an-update-tool-requires-nothing-at-its-door)).
That refusal, and any other the Tool API makes on the input's shape (a
key of the wrong type, a key a create requires left out), is the one
answer not in the shape when it comes through the Tool API's runner
(`drush tool:run`, MCP, the AI connector), which answers it itself:
`{"success": false, "error": "Invalid input:\nvalues: This value should
not be null.", "error_type": "invalid_input"}`. Called directly,
`execute()` answers it in the shape.

## How to try it

```bash
composer require drupal/tool drupal/address
drush pm:install data_surface_tool data_surface_address
drush tool:list
```

`drush tool:info data_surface:field.instance:reuse` prints the input
definitions. The title is the operation's label, and the description is
the operation's own description followed by one line of call rules
that names its kind (`Create:`, `Update:` or `Read only:`). A tool for an operation that creates requires each
key in `values` exactly when the resource requires it, and lists the
declared defaults. One for an operation that changes what exists, such
as `data_surface:registration.step3:configure` or
`data_surface:field.instance:edit`, requires no key and lists no
default at all, because a listing is cached by its clients and a key
left out keeps its current value: each key the resource requires says
"Required; a value already stored stands when left out.", and the
description says "Update: send only the keys to change; a key left out
keeps its value, null clears it, and values {} changes nothing. The
read tool returns the current values." An edit of a thing
that holds no value for a required key is refused by the pipeline, in
the key's own words. A key another narrows says so in its description,
by the path a caller sends it under ("Depends on venue."), and a
refusal says what is allowed for the values sent: example 3's
[README](../data_surface_examples/README.md#when-a-call-is-refused)
shows an agent's retries. Once a tool that needs a subject has its
parameters, its refined `values` defaults each key to what is stored
now, for that one call, and on an edit requires nothing, as its listing
and its door do. The `values` input's `settings` carry every field type's
settings until the storage is known, and refine into the address
settings once `storage` names an address storage. Compare with
`drush tool:info tool_belt:field_add` on the same site, or read
[`COMPARISON.md`](COMPARISON.md), which has both.

`tool:info` shows the Tool API's rendering of an operation, not the
resource's whole contract. The Tool API cannot say a structure chosen by a
sibling key, so variants are flattened to one map: the variant the stored
values choose (example 3's ticket, as the free ticket while `pricing`
is `free`), or every variant's keys with none required before anything
chooses. The full contract, with an `if`/`then` per variant on the key
that chooses it, is the main module's `data_surface.contract_emitter`:
see it in the contract panel below, or, with `data_surface_react`
enabled, at `/surface-api/{resource}`
([`docs/served-contract.md`](../../docs/served-contract.md)). Since
contract 3 the tool and HTTP agree: one call per operation, with a dry
run as a flag (`dry_run` here, `?dryRun=true` there), and every path
in a result a JSON Pointer.

## The read tool

A caller that wants to change a thing usually wants to see it first,
and a listing is not a read: a write tool for a thing that exists lists
no defaults. So every operation
that can be asked on its own and changes a thing that exists has a read
tool beside its write tool, derived by the same deriver under the same
base plugin id:

| Read tool | Inputs |
| --- | --- |
| `data_surface:node.type:edit:read` | `type` |
| `data_surface:field.instance:edit:read` | `field` |
| `data_surface:field.storage:edit:read` | `storage` |
| `data_surface:registration.step1:configure:read`, `step2`, `step3` | nothing |
| `data_surface:entity.content:<entity type>.<bundle>:edit:read`, with `data_surface_entity` | `id` |

- **Which operations.** One that needs nothing and whose context does
  not create, and one that needs a subject and whose parameters name one
  thing whole: a single entity, or a scalar for every identity key.
  `node.type:add`, `field.instance:add` and `field.instance:reuse`
  create, and have none. `ResourceCatalog::reads()` decides, and the
  catalog lists it ("Read on its own"); a context that turns out to
  create is refused when the read runs.
- **Inputs.** The operation's parameters, exactly as the write tool
  declares them, and nothing else: no `values`, no `dry_run`.
- **Output.** `values`: what the resource's composed storage loads, in
  the shape the write tool's `values` input takes (the resource's keys
  less the identity keys the operation knows, keys other modules mount
  under `third_party_settings` included, attached structures and variants
  as nested maps). Its definition is the write tool's `values` map said as an
  output, `InputDefinitions::outputFromInput()`: the same data
  types, labels, descriptions and nesting, so `tools/list` over MCP shows
  the same keys as the input schema, with no constraint and no property
  required. A read reports storage as it is, and a stale value
  ([`docs/semantics.md`](../../docs/semantics.md)) must not fail the
  output validation the Tool API runs on every result; a key storage
  holds nothing for is absent.
- **Secrets.** A key the resource marks secret is never returned, at any
  depth, and is not in the output definition: left out, as the write
  tool's defaults leave it out, not sent as a placeholder.
  `Pipeline\Outbound::secrets()` finds every one, under a key with
  variants in any of them, and cuts both the definition and the values.
- **Every door answers the same.** What the read answers is the one
  projection of stored values (`Pipeline\Outbound::project()`): no key
  the build left out for the account, at any depth, no secret, no key
  that does not apply. The write tool's `values`, on a dry run and on a
  write, go through the same, so neither door says more than the other
  ([decision](../../docs/decisions.md#every-door-projects-what-the-read-tool-projects)).
- **Access.** The write tool's, deliberately, for now: the operation's
  permission, then the resource's access class, for the context the
  parameters build. A caller who may not change a thing may not read it
  either. A parameter that names nothing fails as it does for the write
  tool.

```bash
drush tool:info data_surface:registration.step3:configure:read
drush tool:run data_surface:registration.step3:configure:read --uid=1
drush tool:run data_surface:node.type:edit:read --uid=1 --input=type=page
```

`tool:info` lists the `values` output without its properties; Drush
prints outputs one level deep. The nested schema is what the Tool API's
serializer emits, and what an MCP client sees as `outputSchema`.

## The contract panel

`ContractPanel`, the service `data_surface_tool.contract_panel`,
is a read-only panel any operation route can name in
`_data_surface_panel`. The generic operation form places it inside the
data surface's form, so it rebuilds with the form: every key with its type, label,
requiredness, default, what it allows in words, what it depends on, and
whether it is narrowed right now. Below the table, collapsed, are three
JSON Schema documents: "The schema for these answers", which
`data_surface.contract_emitter` emits for the operation and the form's
values as they stand (variants as `allOf` of `if`/`then`, titled `oneOf`,
`x-surface` with dependsOn and locked, no widget hints); "The full
schema, for any answers", the same emitter's `emitFull()`, which reads
no value and so does not change with the form (every key as declared,
every listable dependency as conditionals); and "What the
Tool API can advertise", the derived tool's input schema as `tool:info`
prints it, with a sentence on what it cannot say. It stays in this
submodule because that second block needs the Tool API's serializer.
The routes of `data_surface_examples` name it.

## Who may run them

A write tool is `ToolOperation::Write`, or `ToolOperation::Read` for an
operation that says it is read only, and destructive when its operation
says so (`ResourceOperationToolDeriver::behaves()`); the MCP bridge
reads both as the tool's annotations. None of the module's own
operations says either, so every write tool here is a `Write` that
destroys nothing, and the access answer has to be the real one, and a
read tool asks the same question. It is the operation's permission, `administer %entity_type_id
fields`, named from the identity the operation's context knows (the
entity type the add tool is given, or the one the storage or field it
names is on), then `FieldInstanceAccess`, which refuses a locked
storage, then the access class of the settings variant the field type
chose, which may refuse (the gated test field type does). A tool asks a
permission as written first, from its id alone, before it reads a
parameter or loads what one names, and refines `values` (which reads
what is stored) only for an account the operation is open to. A refusal
past that gives one reason, "The operation cannot be run by this
account with these parameters.", whether a field or storage does not
exist or an access class refused it, so it never says whether an id
exists; an account holding the operation's permission for what the
parameters name hears the access class's own reason, and the rest is
logged to the tool channel. An account holding a permission as written
(one with no `%key`) is let through when a parameter names nothing, and
the call fails as input to correct, "Not found: there is none with the
id ...", not as access denied, which reads as final.

The operation's permission is also the tool's declared permission
(`ToolDefinition::getPermission()`), so `tool:info` prints it and the
Tool API checks it before reading any input, when it is one permission
as written: `data_surface:node.type:add` declares the node type demo's
permission. A permission with a `%key` placeholder, as the field tools'
`administer %entity_type_id fields`, names a different permission for
each call, and the Tool API has no place for one that depends on the
input: such a tool declares none, `tool:info` prints "Permission:
None", and the tool's own access, which fills the placeholder from the
parameters, is the only check
(`ResourceOperationToolDeriver::declaredPermission()`). That is one rule
with the schema route's refusal: a permission as written is the
operation's first static access answer, decided by the account alone,
and one with a placeholder waits for the subject
(`OperationDefinition::staticPermission()`). The read tool declares the
same one.

### What the listing says about access

A listing is cached by clients, so it says only what the account's own
permissions and roles decide, for the account that asks
([decision](../../docs/decisions.md#access-is-static-or-runtime-read-from-its-cacheability)).
The derived definitions, cached for every account, are no account's:
built for no account (`ResourcesInterface::buildDeclared()`), every key
as declared and each one an access answer could lock or leave out
marked, and derived as the anonymous account, so an option list read
from the site is never a privileged account's
([decision](../../docs/decisions.md#a-static-tool-definition-is-no-accounts)).
A tool instance lists `values` again for the current account, built for
the account alone (`OperationInputs::listedValues()`,
`ResourcesInterface::buildStatic()`), so `tool:info` and anything that
normalizes an instance's inputs see the caller's own listing:

- a key a static access answer locks is a locked property, and one it
  leaves out is not there;
- a key whose access waits for the thing itself (a stored value, State,
  the `user` context, or an answer with no cacheability at all) is there
  and writable, and its description ends with "Whether this may be
  changed is decided once the thing it belongs to is known: a call may
  find it locked or left out." The served contract says the same with
  `x-surface.access: "live"`; the Tool API's normalizer writes its
  schema from typed definitions, which carry a description and no
  extension keyword, so the listing says it in words;
- when that answer is the resource's own, at the top, it marks every
  key, and the tool's description ends with "Every key may be found
  locked or left out once the thing is known." instead, with no key
  repeating it (example 10's `configure` and its read tool, under the
  workflow module). A key whose mark is its own, as example 10's fees
  are, keeps its note. Whether to say it is asked as the anonymous
  account, as the tool is derived, so an answer at the top that is
  static for it says nothing.

Once the parameters arrive, `values` is refined from the resource built
with every answer applied, which is what the pipeline holds a call to.
A consumer that lists from the cached plugin definitions without making
an instance sees every key, as declared, the marked ones saying a call
may find them locked or left out. The MCP bridge's config deriver makes
an instance when it derives its MCP tools and caches what it normalized
for every client, so its `tools/list` is the listing of the account that
caused that derivation: the bridge's caching, open there.

The tool asks again inside `doExecute()`. `ToolInterface::execute()`
runs no access check of its own, so a caller reaching a tool directly
from PHP would otherwise write without one.

## Notes for the Tool API

Found while writing the bridge; none of them were worked around by
changing the Tool API.

- **A context definition has no settings and no examples.** A core data
  definition carries both. `ContextDefinition::getDataDefinition()`
  rebuilds its data definition from the data type alone, so type settings
  are lost, and there is nowhere to put the examples JSON Schema has a
  keyword for. Both are dropped in conversion.
- **Every constraint but two is invisible to the schema normalizer.**
  `ContextDefinitionNormalizer::applyConstraintSchema()` reads `Choice`
  and `AllowedValues`, matched by plugin id and never with `instanceof`,
  so a value list declared as anything else — `LabeledChoice`, or an
  existence constraint such as `PluginExists`, `Country` or
  `LanguageExists` — would not reach the advertised schema at all. The
  bridge asks `data_surface.options` for the list, which is the one place
  that reads a constraint as one, and adds a plain `Choice` carrying
  those values beside the constraint that named them. The labels
  themselves have nowhere to go: JSON Schema's `enum` is a bare list, and
  the normalizer has no convention for per-value labels.
- **Defaults do not reach the schema for maps, lists, or falsy values.**
  The normalizer emits `default` only on the scalar branch, and only when
  the value passes a truthy test, so an empty list default and a null
  default are both dropped. The converted definitions carry them; the
  JSON does not.
- **`setLocked()` has no effect below the top level.** A locked resource
  key converts to a locked property definition, but only top level inputs
  are filtered by it, and the map normalizer walks every property. The
  statement is carried anyway.
- **A required map property's default is not honored.** A resource's
  required key must hold a value, which a default or a stored value
  can supply. `TypedInputsTrait::validateInputValue()` refuses a
  required property the payload leaves out ("This property is
  required.") whatever its default, and the `!isset($default_value) &&
  isRequired()` check that does honor a default covers top level
  inputs only (issue 5 of the Tool API gaps raised upstream). So a tool
  for an operation that changes what exists requires no key at all, in
  its listing and at its door, and says on each key the resource
  requires that a value already stored stands when left out; the
  pipeline judges the merged document, and refuses a required key only
  where nothing is stored for it. A create says `required` as the
  resource does, since nothing is stored there. `ExamplesToolTest` pins
  a partial update that leaves a required key out.
- **Input validation runs before the tool does, against the listing.**
  The Tool API holds every input to its definition before the tool
  runs, and a map's property refusal comes out nested, "values:
  (property room) The value you selected is not a valid choice.", which
  the MCP bridge prints without the path. Held to the listing, a key
  another narrows is refused against its widest answer, with nothing
  said about the answer that applies, and a caller needs a second try.
  So the tool holds `values` to its shape alone there (types, the keys
  it requires, none on an update, its nesting: `validateInputValues()`,
  `InputDefinitions::shapeOf()`) and leaves every rule to the pipeline,
  which narrows `values` from the document sent and says what is allowed
  for it ([decision](../../docs/decisions.md#a-refusal-names-what-it-depends-on)).
  A self-refinement through `input_definition_refiners` would not do:
  a refiner's own dependencies are validated before it runs, so a
  document that breaks the listing is never narrowed, and a document
  narrowed is refused in the Tool API's words. A way for a tool to hand
  the Tool API the violations of an input, worded and with their paths, would let
  the bridge keep the Tool API's validation step for rules too.
- **Idempotence is the operation kind's, not the tool's.**
  `ToolOperation::isIdempotent()` is a property of the kind, and every
  kind that modifies (`Write`, `Trigger`) is not idempotent, so a tool
  for an operation that changes what exists cannot say it is safe to
  repeat while one that creates says it is not: both are `Write`, and
  the MCP bridge annotates both `idempotentHint: false`. `Write` is the
  least wrong kind: every idempotent kind does not modify, and would
  also say the tool changes nothing. Both schema documents state the
  operation's own answer under `x-surface.operation`. An idempotent flag
  on the definition, beside `setDestructive()`, would let it say so
  ([decision](../../docs/decisions.md#an-operation-states-how-it-behaves)).
- **A declared permission cannot depend on the input.**
  `ToolDefinition::setPermission()` takes one route-style string, checked
  before any input is read, so a permission named from what a call is
  about (`administer %entity_type_id fields`) has nowhere to go: those
  tools declare none, and `tool:info` prints "Permission: None" for a
  tool its own `checkAccess()` gates. A permission callback, or
  placeholders filled from named inputs, would let them say it.
- **A value of the wrong type is refused before the tool runs, with no
  code and no type named.** The shape check above is the Tool API's, and
  a runner answers its refusal itself, outside the tool's result shape:
  a deposit of `12.5` for an integer, or `"lots"` for a number, comes
  back as "Invalid input: values: (property deposit) This value should
  be of the correct primitive type.", with no `code`, no `path` and no
  word of the type wanted. A caller cannot tell it from any other input
  refusal without parsing the sentence. Called through `execute()`, the
  tool answers it in its own shape, `code` and `path` included; a runner
  never gives it the chance. A type mismatch that named the type wanted
  (core's `PrimitiveType` constraint has its type to hand), or a way for
  a runner to hand the refusal to the tool to answer, would close it.
  Found by the fourth fresh-eyes run (entry 19).

## Note for core

`TypedDataManager::getPropertyInstance()` caches item prototypes by root
data type and property path, not by field config object, so asking two
different unsaved `FieldConfig` objects for their first item hands back
two clones of the first one's item, and storage built for the second
writes to the first one's entity. A tool hits this immediately, because
it describes an unsaved field while refining its inputs and creates
another while executing. The field type trait sidesteps it by building
the item straight from `FieldConfigBase::getItemDefinition()`, which a
field config caches on itself and binds to itself.

Both notes are summarized in
[`docs/core-gaps.md`](../../docs/core-gaps.md).
