# Data Surface - Tool API bridge

Two field instance tools whose `settings` input is the field type's own
data surface, so the A/B against the free-form Tool Belt pair is a fair
one: same seven inputs, same execution, different answer to "what may the
settings be?".

## What it shows

`data_surface:field_add` and `data_surface:field_update` mirror
`tool_belt:field_add` and `tool_belt:field_update` input for input. The
Tool Belt pair refines `settings` from the field type's config schema
once the field type is known, which for the `address` field type yields
three types, a nested `override` key with nothing to put a property name
in, a deprecated `fields` key offered as an ordinary one, and no
vocabulary, labels or defaults anywhere below the top level.

Here the same input is converted from the surface the field type
declares. [`COMPARISON.md`](COMPARISON.md) holds both JSON Schema
documents side by side, generated by `scripts/generate-comparison.php`; `FieldToolsComparisonTest` asserts the checked-in file has not drifted rather
than written by hand.

Three pieces:

- `FieldSurfaceLocator` — given a field config entity, saved or not,
  finds the surface and the target the field item declares, or NULL.
  Nothing field type specific.
- `SurfaceInputDefinitions` — converts core data definitions into the
  Tool API's input definitions: type, label, description, required,
  default value and constraints, with maps and lists becoming the Tool
  API's own map and list input definitions.
- The two tools. They contain no settings logic: refining is a lookup
  plus a conversion, and executing is one call to
  `DataSurfacePipeline::submit()`, which accepts, validates, prepares and
  commits.

### One deliberate difference from the Tool Belt pair

Tool Belt's update tool strips every null from the settings it is given
before merging them over the stored ones, so a setting can be set but
never cleared. Here the pipeline merges the payload over what the target
loads, key by key and at every depth, and a null is a value like any
other. Sending `{"field_overrides": {"organization": null}}` removes that
one override and leaves the rest alone, which is what a caller correcting
one mistake actually wants to say.

## How to try it

```bash
composer require drupal/tool drupal/address
drush pm:install data_surface_tool data_surface_address
drush tool:list
```

`drush tool:info data_surface:field_add` prints the input definitions.
The `settings` input carries nothing useful until the field type is
known, and refines into the address surface once `field_type` is set.
Compare with `drush tool:info tool_belt:field_add` on the same site, or
read [`COMPARISON.md`](COMPARISON.md), which has both.

## Who may run them

Both tools are `ToolOperation::Write`, so the access answer has to be the
real one and it must not be assembled from what the caller sent.

| Tool | Access |
| --- | --- |
| `data_surface:field_add` | `administer <entity type> fields`, and only after the entity type manager confirms the entity type exists |
| `data_surface:field_update` | `$field->access('update')` on the field config entity the values name |

Updating asks the entity, which is where the answer belongs: core's field
config access handler delegates to the field storage, which is the one
place `administer <entity type> fields` is spelled, and a module refining
field access through the entity access hooks is heard. Adding has no
field config entity to ask yet, so it falls back to that permission — but
the entity type id arrives as tool input, and an id is never spelled into
a permission name before the entity type manager has said it names
something. An id naming nothing is refused outright, and a refusal never
says whether the field or the entity type exists.

Both tools ask again inside `doExecute()`. `ToolInterface::execute()`
runs no access check of its own, so a caller reaching a tool directly
from PHP would otherwise write without one.

## Notes for the Tool API

Found while writing the bridge; none of them were worked around by
changing the Tool API.

- **A context definition has no settings and no examples.** A core data
  definition carries both. `ContextDefinition::getDataDefinition()`
  rebuilds its data definition from the data type alone, so type settings
  are lost, and there is nowhere to put the examples JSON Schema has a
  keyword for. Both are dropped in conversion.
- **Every constraint but two is invisible to the schema normalizer.**
  `ContextDefinitionNormalizer::applyConstraintSchema()` reads `Choice`
  and `AllowedValues`, matched by plugin id and never with `instanceof`,
  so a value list declared as anything else — `LabeledChoice`, or an
  existence constraint such as `PluginExists`, `Country` or
  `LanguageExists` — would not reach the advertised schema at all. The
  bridge asks `data_surface.options` for the list, which is the one place
  that reads a constraint as one, and adds a plain `Choice` carrying
  those values beside the constraint that named them. The labels
  themselves have nowhere to go: JSON Schema's `enum` is a bare list, and
  the normalizer has no convention for per-value labels.
- **Defaults do not reach the schema for maps, lists, or falsy values.**
  The normalizer emits `default` only on the scalar branch, and only when
  the value passes a truthy test, so an empty list default and a null
  default are both dropped. The converted definitions carry them; the
  JSON does not.
- **`setLocked()` has no effect below the top level.** A locked surface
  key converts to a locked property definition, but only top level inputs
  are filtered by it, and the map normalizer walks every property. The
  statement is carried anyway.
- **Input validation runs before the tool does.** Because the added
  `Choice` constraint validates as well as describes, a bad settings
  value is refused by `getExecutableValues()` and the tool's own pipeline
  never sees it. The refusal is still path aware, in the Tool API's
  spelling rather than the pipeline's.

## Note for core

`TypedDataManager::getPropertyInstance()` caches item prototypes by root
data type and property path, not by field config object, so asking two
different unsaved `FieldConfig` objects for their first item hands back
two clones of the first one's item — and a target built from the second
writes to the first one's entity. A tool hits this immediately, because
it describes an unsaved field while refining its inputs and creates
another while executing. The locator sidesteps it by building the item
straight from `FieldConfigBase::getItemDefinition()`, which a field
config caches on itself and binds to itself.

Both notes are summarized in
[`docs/core-gaps.md`](../../docs/core-gaps.md).
